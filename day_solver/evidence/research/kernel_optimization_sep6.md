# Kernel and search-budget experiments, 6 September

All experiments use only public v3 input or proposals generated by our own cold
constructor. The original replay routes never enter a solver. These are exposed
development cases, not new held-out coverage.

## Candidate ranking

The old compact neighborhood fully sorts every generated candidate, then keeps
some globally best candidates and cycles through move groups. The new kernel
selects the needed indices with nth_element and sorts only the retained prefixes.
Keeping at most shortlist entries per group is sufficient: earlier entries in
that group either fill a slot during group selection or already occupy a global
slot. Candidate generation, deduplication, scoring and tie rules are unchanged.

All 432 comparisons matched, including 1,734,062 generated and 29,404 selected
candidates. Paired component time was 10.731 versus 10.362 seconds, about 3.4%
less. The wrapper passed the full regression suite.

V30 changes only this kernel relative to V27. It passes all 81 development
controls. A paired two-repetition comparison across those cases passed all 324
runs and 7,776 independent hours. Total time was 65.812 versus 64.299 seconds,
2.3% less. The real-day median was 239.175 versus 229.716 ms. This is a small gain
on a shared host, not a reliable promise for every input. V30 remains unselected.

## Pattern cargo and route inputs

The scoring kernel repeatedly visits the same bundle actions to compute cargo
shortages and route input counts. Precompute each bundle's net change and minimum
starting cargo by item. For starting cargo c, required cargo r and net change d,
the shortage is max(0, r-c); final cargo is c+d+shortage. Compose these summaries
in route order. Reset cargo at route boundaries and apply shared shed allowances
after summing shortages, exactly as in the original scoring heuristic.

This does not label fertilizer sources or fix animal-to-crop pairings. Summaries
retain the ordered effects of production and consumption inside each bundle.
The exact scheduler and strict replay remain responsible for actual timed
inventory and legal actions.

Precompute each bundle's input bitmask for route length; popcount of their union
replaces repeated action scans. The C API retains an explicit list path when
there are more than 64 item kinds. The game uses fewer than that.

All 432 neighborhood comparisons matched with the new scorer. Paired component
time was 5.630 versus 4.997 seconds, 11.3% less. The isolated wrapper passed the
full regression suite. V31 integrates only this scoring change into V27 and passes all 323 real
development days plus 9 synthetic controls. Paired two-repetition testing passed
all 324 runs, but total time was essentially unchanged: 62.195 versus 62.167
seconds. Real-day median was 220.705 versus 227.654 ms. Do not claim a whole-day
gain from this kernel yet. The 130 ms repair budget with the faster kernel also passed all 324 trials but
raised total time from 66.446 to 93.603 seconds. Reject this smaller reduction
too. The fixed time limit and sensitivity of fallback paths prevent a simple
conversion of kernel savings into shorter day times.

## Rejected budget changes

Reducing all quick route repair budgets from 150 to 15 ms passed all 324 runs,
but total time rose from 113.995 to 304.130 seconds. Several days fell into much
slower fallback branches. Reject the global reduction.

V29 tries one cheap 15 ms constructor/120 ms completion attempt before the
original search and includes the ranking kernel in both modes. All 324 paired
runs passed, but enabling the extra attempt raised total time from 59.644 to
65.973 seconds. Real-day median rose from 211.591 to 279.155 ms. Reject the extra
attempt. Keep the original search order and repair budgets.

## Bound expensive repair checks

New native_bounded_repair uses known nonnegative repair terms to reject a
candidate only when its lower bound already exceeds the current best complete
score. Ties remain. All 72 fixed-iteration constructor comparisons preserve the
resulting proposals. It skips 18,619 of 52,070 eligible expensive checks and cuts
paired component total from 12.219 to 11.554 seconds (5.4%). Search diagnostic
counts change, not the selected routes in these controls. V32 integrates this
only into quick construction; whole-day checks are pending.

V30 broader251 and slow242 checks have also closed fully strict, with 6,024 and
5,808 independent hours. Its earlier paired 2.3% gain remains the appropriate
whole-day causal comparison; separate shared-host totals are not paired gains.


V32's whole-day test closed all 324 runs strictly with 7,776 independent hours.
Paired totals were 59.280 seconds for V30 and 59.675 for V32, effectively neutral
(0.7% more time). Do not adopt the bounded repair as a whole-day speed gain. Its
component savings remain real within the 72-comparison scope. No broader or
fresh cohort is needed for this rejected public integration.

## Constructor stage profile

System perf access is disabled, so native_constructor_profile instruments major
constructor stages. On the 128 quick attempts made by V30's closed development
run, repeated twice with one process, repair consumes 22.918 of 30.388 seconds
(75.4%); route search consumes 6.965 seconds (22.9%). Routing data takes 1.2%.
Nearly every alternate balancing attempt spends at least 140 ms in repair.
This explains why faster kernels often produce more search without a shorter
call. More input caching is a low-priority target for this workload.

V33 tested stopping balance improvement once the heuristic feasibility score
is zero. Pickup/checkpoint optimization retains its old stopping condition;
quick construction uses neither. This changes proposal selection and is not a
proof of feasibility. Exact completion and strict replay remain mandatory.
All 81 controls and the full regression suite passed. The paired comparison
closed with 324 strict schedules and 7,776 independently checked hours:
V30 took 59.30717846 seconds in total and V33 took 58.25607961 seconds (1.8% less).
Broader development and slow-case checks were not run. V33 remains unselected.

## User-requested seal and stop

The user requested sealing the fastest broadly validated pipeline, then quitting.
V30 is now the main result in `../result/`; V20 is retained as the held-out
reference. This is an artifact selection, not a new unseen coverage result.
Gate14's two failures remain unresolved. V34 (`native_floor_repair`) and
