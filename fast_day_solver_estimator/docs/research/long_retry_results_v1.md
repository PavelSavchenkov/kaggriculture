# Deciding which failed calls deserve a longer retry

This is a caller policy after a completed solver attempt, separate from the pure unscheduled labor estimator. The target is verified recovery from an exact failed three-second query when retried for thirty seconds. It does not predict physical infeasibility. All current results below are development evidence with complete family exclusion, not fresh-family acceptance.

The audit matches 1,333 long calls to the same failed short query, including full input and backend hashes, horizon, workforce and hiring slots. There are 440 physical contracts, 1,300 exact input hashes, 124 successful retries and 1,209 unresolved retries. The latter consume 36,396.55 CPU seconds. The calls were selected by earlier near-upper-bound and unresolved-case policies; this is not a random population. Repeated physical contracts remain in the same excluded/bootstrap family.

Adding physical/calendar features, a known-certificate indicator and the observed failed-call timing improves whole-family Brier from 0.09248 for the old three-second model to 0.05832. The forest's gain is concentrated in cases without a certificate at any workforce. On prior-certified calls, Brier is slightly worse, 0.08578 versus 0.08318. A post hoc rule scaling the old probability by 0.1 only when no certificate exists reaches 0.05680 overall, but does not improve within-state ranking and loses rare recoveries when used with a fixed probability cutoff.

The decision replay has 543 separate contract/round states, with one to three available retry queries each. There are 365 prior-certified states and 178 initially unresolved states; six of the latter have a recorded recovery somewhere in their options. One-, two- and three-call allowances are soft thirty-second backend calls, not hard 30/60/90 CPU-second budgets. Selection cannot access untried outcomes or recorded future CPU.

The new forest does not justify export. With two calls, it saves only 0.112 CPU seconds per state against the old probability control, with a family interval crossing zero, and raises mean common-success bills by 48.09. With all three calls, its final bills are identical but there is no speed gain. The simple nearest-workforce control remains strong. Probability threshold 0.02 on the new forest misses four of six recorded first certificates; the apparently cheaper result is not a quality-preserving improvement.

A narrower rule is worth prospective testing: when a certificate already exists, use the existing probability model to rank expected immediate hire-bill saving per predicted CPU, and stop below 0.01 cash per CPU second. Predict long CPU as a probability mixture of arithmetic successful/unsuccessful retry means. On the 365 known-certificate development states, this reduces CPU from 21,297.67 to 15,268.39 (28.31%) versus the same ordering without stopping, while retaining every best recorded bill. This cutoff was selected on development evidence. The compute-value sweep is a sensitivity study, not an assumed user preference or proof that the rule transfers.

The candidate uses the existing frozen C++ probability model plus a small C++ selection rule. It does not require the newly fitted forest. Cases without any certificate remain outside this optional refinement policy. They must not be silently discarded, and their rare expensive recoveries remain visible in the main estimator's error reports.

Artifacts: `runs/long_retry_dataset_v1`, `runs/long_retry_study_v1`, `runs/long_retry_replay_v1`, and `runs/long_retry_utility_v1`. The C++ API is `include/long_retry_policy.hpp`; numerical checks and inference charges must precede a fresh retry gate.
