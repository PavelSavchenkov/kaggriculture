# Reference labels and hiring rules

The first reference run uses 400 development physical contracts selected by a fixed hash order before solve outcomes. It has 3,523 candidate-workforce queries. Final-day cases are kept separate because the game ends after hour22.

For each contract, remove source hires and construct 39 possible hire slots: the earliest chronological slots before hour23 not occupied by a fixed purchase/land order. Workforce k activates the first k-1 slots. This menu does not depend on the source answer count. It is a physical scheduling rule; actual sale-slot/funding constraints still belong to the full compiler.

The true target for this rule is minimum feasible k. The first pass runs the unchanged root V30 solver for three soft seconds per query, one fallback thread, four independent processes. Search every count from a safe task-capacity lower bound through two above the largest observed source count (capped at40). This query-range choice is label-building metadata and is never an inference feature. More workers can be examined later if the range produces no certificate.

Every returned schedule is independently replayed and saved. Record FEASIBLE or UNKNOWN, budget, CPU/wall time and schedule hash. A source schedule is not automatically feasible under the changed hire calendar. Never promote a restricted solver's INFEASIBLE status to a general proof.

The cheapest found k is a feasible upper bound. Compute task/travel/distance-shell lower bounds separately. Deeper searches will concentrate on wide intervals, costly decisions and uncertain rankings; audit that this allocation does not make test labels easier than training labels.

An additional operational prediction may estimate whether a specified compiler budget certifies a queried workforce. Here UNKNOWN is a legitimate unsuccessful-search outcome, but remains censored evidence about physical feasibility. Do not conflate these two targets.

## Fresh replay extraction

Downloaded replay dictionaries are alphabetized. This differs from live engine dictionary order, and the original root parity exporter assumes live order. The first adapter therefore failed at step0. The corrected adapter orders products explicitly and compares all observed inventory counts with carried keys sorted in both representations. The live C++ simulator retains actual insertion order for execution and overflow decisions.

This verifies all720 observed states and719 transitions, excluding unrecorded carried-dictionary insertion order. Exact per-step cash, stock, farms, ages, yields, worker positions, inventories and service state still match. Do not claim that the API exposes the original carried-key order.

Extract only the selected development team's days from each replay. The opponent's days are not training examples merely because the replay contains both seats. Preserve source-overflow and other rejected contracts explicitly. Final29th-index days need separate terminal handling.
